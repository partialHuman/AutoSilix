## 5. Target Architecture

Build SilicaForge as a modular Python application that orchestrates existing EDA tools.

It is not a new synthesis engine, place-and-route engine, transistor simulator, or signoff engine.

Its core value is reliable orchestration, configuration management, artifact provenance, failure handling, metrics extraction, experiment tracking, and reporting.

Use a sequential stage dependency graph for the initial version. Design interfaces so a more advanced workflow graph can be introduced later without requiring a complete rewrite.

The architecture must contain the following components.

### 5.1 CLI

Implement a command-line interface using a maintained Python CLI library such as Typer, or use another suitable library if the workspace already has a consistent choice.

The intended interface should support commands equivalent to:

```bash
silicaforge --help

silicaforge validate \
  --config configs/designs/sequence_detector.yaml

silicaforge run \
  --config configs/designs/sequence_detector.yaml

silicaforge status \
  --run-id RUN_ID

silicaforge report \
  --run-id RUN_ID

silicaforge compare \
  --runs RUN_ID_A RUN_ID_B

silicaforge tools
```

These are target commands, not existing implementations. Implement and test the actual syntax.

Include appropriate exit codes, helpful error messages, structured logging, and command help.

Do not make the CLI depend on the current working directory when it can reliably resolve project paths.

### 5.2 Configuration manager

Implement versioned YAML configuration files.

Validate:

- Schema version.
- Design name and source paths.
- Testbench and simulator settings.
- Synthesis options.
- Platform and PDK selection.
- Timing constraints.
- Clock period and units.
- I/O delays and loads when required by the flow.
- Physical-design parameters.
- Output locations.
- Enabled workflow stages.
- Tool executable availability when execution requires it.

Reject malformed or invalid configurations before starting EDA processes.

Distinguish configuration errors from missing optional tools and execution failures.

Use a documented schema. JSON Schema or an equivalent validated Python model is acceptable.

Do not allow arbitrary configuration values to silently alter execution behavior.

### 5.3 Workflow engine

Implement a stage-oriented workflow engine.

Each stage must have:

- A stable stage identifier.
- Declared inputs and outputs.
- Prerequisites.
- Execution status.
- Start time, end time, and duration.
- Captured stdout and stderr.
- Exit code.
- A machine-readable error summary.
- Validation of expected outputs.
- References to generated artifacts.

Use clearly documented states, including:

- `PENDING`
- `RUNNING`
- `PASS`
- `FAIL`
- `SKIPPED`
- `NOT_RUN`
- `UNSUPPORTED`

You may introduce additional states if necessary, but define their semantics.

The engine must support:

- Sequential dependency enforcement.
- Configurable per-stage timeouts.
- Graceful interruption where practical.
- Nonzero exit-code handling.
- Detection of missing expected outputs.
- Preservation of partial artifacts after failures.
- Clear distinction between a failed stage and a skipped downstream stage.
- Optional fail-fast behavior.
- Safe reruns using new run identifiers by default.

Do not silently resume a stage using stale artifacts. Any reuse or resume feature must verify the relevant inputs and artifact provenance.

### 5.4 Tool adapters

Implement isolated adapters for:

- RTL simulation or linting.
- Yosys synthesis.
- OpenROAD physical-design execution.

Create clear adapter interfaces so each tool can be replaced or extended independently.

Use argument arrays and subprocess APIs instead of constructing unsafe shell command strings.

Capture stdout and stderr, process return codes, execution duration, and tool version information.

Do not assume that every physical-design flow uses the same Tcl commands, directory layout, platform variables, or report format.

Where possible, use a supported, existing platform reference flow instead of inventing a new flow from scratch.

For each supported tool, implement:

- Availability detection.
- Version detection.
- Input validation.
- Command preparation.
- Execution.
- Output validation.
- Error reporting.
- Relevant report discovery.

Provide clear error messages when executables are missing.

Do not pretend that a tool adapter can run a stage when its required external tool or configuration is absent.

### 5.5 Artifact manager

Create unique, isolated run directories.

Use a structure equivalent to:

```text
runs/
└── sequence_detector/
    └── RUN_ID/
        ├── manifest.json
        ├── config/
        ├── logs/
        ├── reports/
        ├── netlists/
        ├── databases/
        ├── layout/
        └── metrics/
```

The exact layout may be adjusted to fit the actual EDA flow, but document the final convention.

The artifact manager must:

- Prevent accidental run-directory collisions.
- Preserve the effective configuration snapshot.
- Record tool and platform versions.
- Record source revision where available.
- Compute configuration and artifact hashes where useful.
- Preserve raw logs and reports.
- Record output paths relative to the run directory where practical.
- Identify incomplete and failed runs.
- Avoid committing large generated outputs by default.

Never claim a layout or netlist exists solely because a stage was configured to generate one. Verify the actual file and its basic validity.

### 5.6 Manifest and provenance

Define a versioned manifest schema.

Include, where available:

- Schema version.
- Run ID.
- Design identifier.
- Start and completion timestamps.
- Overall orchestration status.
- Per-stage status.
- Effective configuration and its hash.
- Source revision.
- Dirty working-tree information where available.
- Operating system and relevant environment information.
- Tool versions.
- PDK/platform identity and revision.
- Timing constraints and units.
- Artifact paths and hashes.
- Metric values and units.
- Metric source-report references.
- Errors and warnings.
- Explicit unavailable or unsupported checks.

Do not store secrets or sensitive environment values in manifests.

Ensure a manifest remains useful after a failed or interrupted run.

### 5.7 Metrics and report engine

Implement metrics extraction separately from workflow execution.

Initially support the metrics actually emitted by the selected reference flow, including where available:

- Synthesized cell area.
- Placed cell area.
- Core and die area.
- Utilization.
- Clock target.
- Setup slack.
- Worst negative slack.
- Critical-path delay.
- Buffer counts.
- Congestion indicators.
- Unrouted-net counts.
- Routing violations.
- Dynamic and leakage power when valid data exists.
- DRC/LVS outcomes when supported.

Every metric must have:

- A name.
- A numeric value or an explicit unavailable state.
- Units where applicable.
- A source stage.
- A source report or artifact.
- An extraction method or parser version.
- Relevant analysis conditions, such as timing corner, when available.

Do not convert missing values to zero.

Do not mix pre-route and post-route timing without identifying the distinction.

Do not report power as meaningful when the required libraries, activity information, and analysis conditions are missing.

Preserve raw reports even when a parser fails.

Implement robust report parsing with tests for malformed, incomplete, and changed report formats.

Generate:

- A machine-readable JSON summary.
- A CSV metrics export.
- A human-readable Markdown report.
- A comparison report for compatible runs.

A visual dashboard is optional and should not delay a functioning CLI.

### 5.8 PPA experiment management

After reliable single runs work, add experiment support.

Allow controlled variations of selected parameters such as:

- Clock period.
- Core utilization.
- Supported synthesis options.
- Equivalent RTL variants.
- Later, pipeline or architecture variants.

Store each experiment as a reproducible configuration and run.

Provide comparison logic that:

- Checks PDK/platform compatibility.
- Checks relevant toolchain compatibility.
- Identifies differing constraints.
- Identifies differing implementation stages.
- Identifies missing metrics.
- Preserves the provenance of each result.
- Flags incomparable measurements instead of producing misleading conclusions.

Do not claim a universal optimum based on a small experiment set.

Automated parameter sweeps should be introduced only after single-run reproducibility and metrics validation work correctly.
